# حاسب نفسك | رفيقك للمحاسبة اليومية

موقع ويب متكامل لمساعدة المستخدم على متابعة أعماله اليومية من العبادات والأذكار والأعمال الصالحة، تسجيل ما أنجزه منها، حساب نسبة الإنجاز، وإصدار تقرير يومي منسق يمكن نسخه ومشاركته عبر واتساب.

المشروع مبني باستخدام **React + Vite + Tailwind CSS** ويرتبط بقاعدة بيانات **Supabase (PostgreSQL)** مع تفعيل **Row Level Security (RLS)** لعزل وحماية بيانات كل مستخدم.

## ⚙️ خطوات ربط المشروع بمشروع Supabase (إلزامية)

1. **أنشئ مشروعًا جديدًا** في لوحة تحكم [Supabase](https://supabase.com).
2. **اذهب إلى Settings > API** وانسخ القيم التالية:
   - `Project URL` → ضعها في `VITE_SUPABASE_URL`
   - `anon public` key → ضعها في `VITE_SUPABASE_ANON_KEY`
   - ⚠️ لا تستخدم أبدًا مفتاح `service_role` في واجهة المستخدم.
3. **أنشئ ملف `.env`** في جذر المشروع مستندًا إلى `.env.example`:

   ```env
   VITE_SUPABASE_URL=https://your-project-ref.supabase.co
   VITE_SUPABASE_ANON_KEY=your-public-anon-key-here
   ```

4. **نفّذ سكربت قاعدة البيانات** في محرر SQL داخل لوحة تحكم Supabase (SQL Editor):
   - افتح الملف `supabase/schema.sql`
   - انسخ محتواه पूरीًا والصقه في محرر SQL ثم شغّله (`Run`).
   - هذا السكربت ينشئ الجداول الأربعة، ويزرع 35 عملاً افتراضيًا، ويفعل RLS، وينشئ السياسات، ويضيف محفّزًا تلقائيًا لإنشاء الملف الشخصي عند التسجيل.

5. **شغّل المشروع محليًا** (بعد تثبيت Node.js):
   ```bash
   npm install
   npm run dev
   ```
   سيفتح الموقع على `http://localhost:5173`.

6. **للبناء للإنتاج**:
   ```bash
   npm run build
   ```
   مخرجات البناء ستكون في مجلد `dist/` ويمكن رفعها على أي خدمة استضافة ثابتة (Netlify, Vercel, GitHub Pages، إلخ).

## 🗄️ بنية قاعدة البيانات (مختصر)

| الجدول | الغرض | الحقول الأساسية |
|--------|-------|----------------|
| `profiles` | ملف المستخدم الشخصي الإضافي | `id` (مرتبط بـ auth.users)، `full_name`، `circle_name`، `created_at` |
| `daily_tasks` | الأعمال اليومية الافتراضية المشتركة (35 عملاً) | `id`، `title`، `category`، `sort_order`، `is_active`، `created_at` |
| `daily_reports` | تقرير المستخدم في يوم محدد (تقرير واحد لكل مستخدم لكل تاريخ) | `id`، `user_id`، `report_date`، `gregorian_date`، `hijri_date`، `created_at`، `updated_at` |
| `daily_report_items` | ربط الأعمال بتقرير المستخدم يومياً | `id`، `report_id`، `user_id`، `task_id`، `task_title`، `is_completed`، `created_at`، `updated_at` |

### قيود سلامة البيانات
- `unique(user_id, report_date)` على جدول التقارير لضمان تقرير واحد لكل مستخدم في اليوم.
- `unique(report_id, task_id)` على جدول بنود التقارير لمنع تكرار العمل نفسه داخل التقرير الواحد.
- مفاتيح خارجية (Foreign Keys) تربط السجلات بالمستخدمين والتقارير والمهام مع `on delete cascade` للحفاظ على الاتساق.
- محفّز تلقائي `handle_new_user` يُنشئ ملفًا شخصيًا في `profiles` عند إنشاء كل حساب جديد في Supabase Auth.

## 🔐 حماية بيانات المستخدمين (RLS)

هذا الشرط الأساسي في المشروع وقد تم تنفيذه فعليًا في `supabase/schema.sql`:

1. تم تفعيل **Row Level Security** على كل جدول يحتوي على بيانات خاصة (`profiles`, `daily_reports`, `daily_report_items`).
2. جدول `daily_tasks` عام للقراءة فقط للأعمال النشطة (`is_active = true`)، ولا يمكن للمستخدم العادي تعديله أو حذفه.
3. السياسات تعتمد على `auth.uid()` للتحقق من هوية المستخدم المصادق عليه.
4. بالنسبة لجدول `daily_report_items`, السياسات لا تكتفي بمطابقة `user_id` فحسب، بل تتحقق أيضًا من ملكية التقرير المرتبط (`report_id`) عبر وجود سجل في `daily_reports` يخص نفس المستخدم.
5. لا يُخزَّن أي مفتاح سري (`service_role`) في واجهة المستخدم؛ يُستخدم فقط مفتاح النشر العام (`anon key`) ويعتمد على RLS لحماية البيانات.
6. لا توجد صلاحيات إدارية تمنح تلقائيًا لمجرد إنشاء حساب.

## 🧪 نتائج اختبارات الحسابين

تم تصميم المشروع ليتم اختباره باستخدام حسابين مستقلين (أحمد ومحمد) وفقًا للمتطلبات الواردة في البرومبت. **ملاحظة مهمة**: نظرًا لعدم توفر Node.js/NPM/Git ومن دون بيانات اعتماد لمشروع Supabase حقيقي في بيئة التنفيذ الحالية، لم يتم تشغيل الموقع فعليًا ولم يتم إجراء الاختبارات على قاعدة بيانات حية. فيما يلي حالة كل اختبار:

| # | الاختبار | الحالة | ملاحظات |
|---|---------|--------|---------|
| 1 | إنشاء حساب أحمد وتسجيل دخوله | ❌ لم تُنفذ فعليًا | يتطلب مشروع Supabase حقيقي ومفاتيح اتصال |
| 2 | إنشاء حساب محمد وتسجيل دخوله | ❌ لم تُنفذ فعليًا | يتطلب مشروع Supabase حقيقي ومفاتيح اتصال |
| 3 | ظهور بيانات أحمد فقط لأحمد | ❌ لم تُنفذ فعليًا | تُحقق عبر سياسات RLS في `schema.sql` |
| 4 | ظهور بيانات محمد فقط لمحمد | ❌ لم تُنفذ فعليًا | تُحقق عبر سياسات RLS في `schema.sql` |
| 5 | محاولة أحمد الوصول لتقرير محمد (بال ID) | ❌ لم تُنفذ فعليًا | يجب أن ترفضه سياسة RLS على `daily_reports` |
| 6 | محاولة أحمد تعديل سجل تابع لتقرير محمد | ❌ لم تُنفذ فعليًا | يجب أن ترفضه سياسة RLS على `daily_report_items` |
| 7 | محاولة أحمد حذف سجل تابع لتقرير محمد | ❌ لم تُنفذ فعليًا | يجب أن ترفضه سياسة RLS على `daily_report_items` |
| 8 | رفض قاعدة البيانات للعمليات غير المصرح بها | ❌ لم تُنفذ فعليًا | راجع سياسات RLS في `schema.sql` |
| 9 | تسجيل الخروج والعودة وبقاء البيانات | ❌ لم تُنفذ فعليًا | تعتمد على Supabase Auth وتخزين البيانات في `daily_reports` |
| 10 | استقلالية تقارير الأيام السابقة | ❌ لم تُنفذ فعليًا | يُطبّق عبر `report_date` لكل تقرير بشكل منفصل |
| 11 | عدم وجود مفتاح سري مكشوف في الواجهة | ✅ مطبّق في الكود | يُستخدم فقط `VITE_SUPABASE_ANON_KEY` العام |
| 12 | عدم وجود بيانات ثابتة بديلًا عن البيانات الحقيقية | ✅ مطبّق في الكود | جميع البيانات تُجلب من Supabase عبر العميل |

**لتنفيذ الاختبارات فعليًا**: بعد ربط المشروع بمشروع Supabase حقيقي وتشغيله، أنشئ حسابين منفصلين (أحمد ومحمد) ونفّذ السيناريوهات المذكورة أعلاه وتحقق من أن واجهات Supabase ترفض أي محاولة للوصول إلى بيانات المستخدم الآخر.

## ⚠️ ملاحظات أساسية

- الموقع **حقيقي وقابل للتشغيل** ويتصل بقاعدة بيانات Supabase مباشرة، وليس نموذجًا تجريبيًا يعتمد على بيانات ثابتة.
- لا تُرفق ملف `.env` contenant مفاتيح حقيقية في المستودع العام؛ استخدم `.env.example` كمرجع فقط.
- التاريخ الهجري يُحسب تلقائيًا عبر المتصفح إن أمكن (`islamic-umalqura`)، وإذا تعذر يتم عرضه كغير مؤكد ويمكن للمستخدم تصحيحه يدويًا.
- الأولوية في هذا المشروع كانت لصحة قاعدة البيانات، وفاعلية RLS، ونجاح تجربة المستخدمين، دون إضافة مزايا إدارية أو اجتماعية معقدة قبل استيفاء الشروط الأساسية.
